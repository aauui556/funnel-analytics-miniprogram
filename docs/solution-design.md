# 通用转化漏斗分析小程序 · MVP 方案

> 本文档由一轮需求拷问产出，逐条记录全部决策点、最终结论、推荐理由与被否方案。
> 术语以 `CONTEXT.md` 为准；架构决策的完整推演见 `docs/adr/`；约束清单的实时版本见 `docs/product-brief.md`。

---

## 1. 产品定位

微信**原生**小程序 + **小程序·云开发**，面向三类场景（内容/增长型运营、销售、教培）的**半通用**转化漏斗分析工具。使用者把手里已有的按天汇总数据贴进来，得到一张漏斗图、一条时间趋势线，以及自动标出的异常。

### 设计原则 P1：数据不足时拒绝给结论，绝不猜

这条原则贯穿全篇，统一裁决所有边界情况。它已经落到五处并会继续适用：

1. 导入时阶段名匹配不上就报错，不按位置对齐（D5）
2. 表格方向不自动判断，转置必须由用户触发（D8）
3. 空白单元格视为缺失，不是 0（D9）
4. 凑不齐一个完整周期就不算环比（D12）
5. 样本量不足就不做异常判定（D13、D21）

默认按此处理新边界情况；若要破例，必须在 `docs/adr/` 里写出理由。

## 3. 逐项决策详情

### D1 通用程度：半通用

**结论**：数据模型与计算引擎按通用设计（阶段用数组存），但使用者从 3 个内置模板出发创建漏斗，不面对空白编辑器。

**理由**：完全通用会让首次使用卡在"漏斗阶段怎么填"；阶段自由增删还会立刻把数据模型推向多列方案。

**被否**：① 完全通用（自由建漏斗）；② 先做单一专用场景再抽通用层。

### D2 数据原子单位：聚合人数

**结论**：最小单位是「某漏斗某天某阶段的人数」，由使用者粘贴汇总表录入。

**理由**：三类对象手上通常只有汇总表；用户级流水要求云函数做去重与时间窗口计算，复杂度上升一个数量级。

**被否**：① 用户级事件流水；② 两者都支持。

**必须显式声明**：转化率是各阶段**人数之比**，不是同一批人的转化率。这条口径必须在产品内可见（位置见第 6 节）。

### D3 阶段数量：3–7 段

**结论**：下限 3（少于 3 段不构成漏斗），上限 7（手机屏上再细就没法读）。

**理由**：把"10 个阶段怎么在小屏展示"变成"不让它发生"。

**被否**：① 固定 5 段；② 放开到 10 段。

> 本条经 D22 修订：数量限制仍为 3–7，但**创建时**可在区间内增删。

### D4 存储结构

**结论**：`funnels` 文档内嵌有序 `stages` 数组；`records` 每条文档表示某漏斗某一天的数据，`counts` 数组按下标与 `stages` 对齐。阶段身份由**下标**决定。

**理由**：小程序端单次查询上限 20 条——"一条记录一个数字"的规范化写法会让 7 阶段 × 30 天产生 210 条文档，取一次矩阵要翻十几页。一天一条文档则一次查询即得整块矩阵，且按「漏斗 + 日期」覆盖式更新，重贴不产生脏数据。

**被否**：① 一条记录一个数字（`funnelId, date, stageIndex, count`）；② 多列存储（`stage1_count`…）；③ 内嵌对象 map（阶段改名即脱钩）。

### D5 阶段身份：双轨

**结论**：**存储与对齐用下标，导入匹配用名称**；同一漏斗内阶段名称唯一。

**理由**：粘贴来源是使用者自己的表，行/列顺序大概率与模板不一致，按位置匹配会产生静默错位——数字贴到错误阶段，图表看起来完全正常。按名称匹配把错位变成显式报错。唯一性约束成本极低，线性漏斗里重名本无意义。

**被否**：① 名称可重复 + 按位置匹配；② 名称唯一但仍按位置匹配。

**代价**：使用者改了阶段名后，手里的旧表匹配不上；缓解手段（匹配失败时手动指定对应关系）列入后续迭代。

### D6 数据归属：按用户隔离

**结论**：每个使用者只能读写自己创建的漏斗与记录；安全规则设为「仅创建者可读写」。

**理由**：漏斗数据（线索量、成交率、续费率）是最敏感的经营数据；云开发让这件事近乎零成本。

**被否**：① 所有人共享；② 组织内共享（需要自建组织与成员概念）。

**必须记住的坑**：云函数以管理员身份运行、**绕过**安全规则，因此由云函数写入的文档必须显式带上从 `cloud.getWXContext()` 取得的 `_openid`。漏写不会报错，而是静默读写全库数据。

### D7 录入格式

**结论**：从剪贴板读取制表符分隔的纯文本；**行 = 日期、列 = 阶段**（首列为日期，表头为阶段名）。

**理由**：小程序里没有"打开 Excel 文件"，只能是纯文本；行 = 日期与 D4 的数据模型天然对齐，粘贴到入库几乎零转换；日期在行上时，"缺了哪几天""同一天贴了两遍"一眼可见。

**被否**：① 行 = 阶段、列 = 日期为主格式；② 两种都支持并自动识别方向。

### D8 一键转置

**结论**：提供一键转置按钮，兼容行列为反方向的表。解析失败时提示"要不要试试转置"，预览区常驻按钮；**绝不自动判断方向**。

**理由**：表格方向只有使用者自己知道，程序只能猜，猜错就是整月数据静默错位。转置作用在**原始文本矩阵**上（解析之前），转置后重跑同一套校验；误操作会因表头不再是阶段名而被校验直接拦下，属自愈。

**被否**：只在常驻按钮（不提示）／自动识别并自动转置。

### D9 导入策略：原子

**结论**：任何一处不合法则整批拒绝，一次列全所有问题位置；解析只做无损规范化（去首尾空格、全角转半角、去千分位逗号）；**空白 = 缺失 ≠ 0**。

**理由**：这个工具的全部价值在趋势与转化率上，静默丢一半数据比报错严重得多；把空白补成 0 会凭空造出断崖，且永远不会被发现。

**被否**：① 部分入库；② 尽力修正（空白补 0、缺日期按顺序补）。

### D10 转化率口径

**结论**：图内每段显示**逐步转化率**（本阶段 ÷ 上一阶段，第一阶段为基准）；页面顶部单独显示**整体转化率**（末阶段 ÷ 首阶段）。

**理由**：逐步转化率是唯一能回答"问题出在哪一步"的指标；整体转化率每个阶段都是冗余的；两者都挂在每段上会让 7 段的小屏挤成一片。

**被否**：① 只算逐步；② 只算累计。

### D11 除零显示

**结论**：上一阶段 > 0、本阶段 = 0 → 显示 `0%`（真实结论）；上一阶段 = 0 → 显示 `—`（不可计算）；其中"上一阶段 0 人但本阶段 > 0 人"额外标记为**矛盾数据**。

**理由**：0/0 与 x/0 在数学上不成立；上一阶段为 0 通常意味着"那天没投广告""那天没开课"，显示 0% 会让使用者把"没数据"误读成"灾难"；矛盾数据几乎必然是录入错误，应被标红而不是画成漂亮的上升箭头。

**被否**：① 一律显示 `—`；② 一律显示 `0%`；③ 上一阶段为 0 时显示 `100%`。

### D12 环比周期

**结论**：使用者在 7 / 14 / 30 天中选择，默认 7 天；数据不足以凑齐一个完整周期时显示 `—`。

**理由**：三个场景的节奏不同（运营按周、销售按成交周期、教培按续费周期），固定一个必然得罪另外两个；但放开任意输入会让口径发散、数字不可比。

**被否**：① 固定 7 天；② 任意输入天数。

### D13 异常检测方式：规则式

**结论**：与上一个等长窗口比较，变化超过固定阈值即标记；数据不足以构成窗口时显示「数据不足，暂不判定」。

**理由**：n=3 时标准差没有意义——单个异常值会同时污染均值和方差，检测器会把它自己"解释掉"，输出看似精确实则随机的结论。规则式不依赖样本量，且使用者能看到判定依据、可以验证也可以反驳。

**被否**：① 统计式（均值 ± kσ）；② 不做检测、只展示原始折线。

### D14 检测对象

**结论**：只监控**各步逐步转化率**与**入口人数**两类；中间阶段的绝对人数不单独监控。

**理由**：由 `人数(i) = 人数(1) × 各步转化率连乘`，中间阶段人数的变化已被完全覆盖，单独监控只会产生重复告警。两类信号含义也不同：入口人数是**环境**信号（投放/渠道/排期变化），各步转化率是**过程**信号（流程哪一环出问题）。

**被否**：① 只测转化率；② 检测所有阶段的绝对人数。

### D15 读写分工

**结论**：读取由小程序端直查数据库、计算全在前端；**只有写入**走云函数。

**理由**：① 写入必须走云函数——小程序端没有事务和批量写，D9 的原子导入只有 `db.runTransaction` 给得了；② 读取走客户端直查时安全规则自动生效，且云函数漏写 `_openid` 的失败方式是"读不到自己的数据"（fail closed），而云函数直读是"读到别人的数据"（fail open）——同一个疏漏，代价相差一个数量级；③ 整个数据集约 7 阶段 × 90 天 ≈ 630 个数字，前端毫秒级算完，放云函数则每次切换窗口都要一次网络往返加冷启动。

**被否**：① 读写计算全走云函数；② 云函数取数 + 前端计算。

**代价**：小程序端单次查询上限 20 条，30 天视图需翻 2 页、90 天需翻 5 页；默认 7 天视图一次请求足够。前置条件：两个集合的权限规则都必须是「仅创建者可读写」。

### D16 折线图内容

**结论**：默认显示**整体转化率**一条线，可切换到任一步的**逐步转化率**；不做多线叠加；**入口人数不画进这张图**。

**理由**：7 条线在 375pt 屏幕上无法辨认，且会让使用者去盯"线团的形状"而不是回答"昨天到底怎么样"；入口人数与转化率量纲不同，共轴会让两条线各自失真，双 y 轴又会诱导读出虚假因果。

**被否**：① 只画整体；② 每阶段各一条线。

### D17 异常标注

**结论**：只在异常发生的那一天在折线上打点；图表上方给一行**跨图表**的异常摘要（注明指标与偏离幅度）；每个异常点可点开查看判定依据（「较上期下降 42%，超过 30% 阈值」）。

**理由**：整条线变色会丢掉"到底哪一天"，而时间定位正是折线图的全部价值；区间色带在只有 3–7 天数据时会盖住大半个图表。摘要必须跨图表，因为入口人数的异常不在转化率图上。

**被否**：① 整条线变色；② 背景色带标区间。

### D18 漏斗图形状：梯形

**结论**：采用经典梯形漏斗。

**理由**：形状的辨识度高于等宽卡片列表，符合使用者对"漏斗"的心理预期。

**被否**：① 每阶段一行的卡片 + 横条；② 纯数字化列表。

### D19 宽度比例与标签

**结论**：宽度**严格按人数比例，不设最小宽度**；标签采用**内嵌 + 侧置混合**——宽段内嵌居中，窄段移到同一水平线的两侧空白区与该段垂直对齐（无需引导线）。

**理由**：梯形上宽下窄，越靠下的段两侧空白越大，而它恰恰最需要空间——空间与需求正好反向。严格比例意味着形状只负责说真话，数字由标签负责；不接受最小宽度，是对"不美化"的一次明确选择。

**被否**：① 全部标签内嵌、字号自适应；② 只画形状、点击弹出详情；③ 设置最小宽度（会假装数值更大，失真）。

### D20 0 人阶段

**结论**：宽度为 0，但用**极细虚线**标记该阶段存在。

**理由**：完全不可见会让使用者分不清"这一段彻底断了"和"图没画出来"；把该段移除更糟——上下两段会看起来相邻，直接改变读数。虚线标记与最小宽度性质不同：前者不对数值做任何声张，后者是假装数值更大。

**被否**：① 就让它不可见；② 连同标签一起移除。

### D21 异常门槛

**结论**：相对阈值 **30%**（两指标共用）；参与判定的样本量（转化率的分母、入口人数的窗口总量）低于 **20** 时不判定，显示「样本过小，暂不判定」。

**理由**：纯相对阈值会让"10 人变 15 人"的 +50% 触发告警，而个位数、十几人的阶段在漏斗末端是常态，误报多了使用者会直接关掉这个功能；改用绝对百分点差则对大盘太迟钝、对小盘太敏感。

**被否**：① 纯相对阈值；② 绝对百分点差。

**诚实标注**：20 与 30% 都是**初始猜测值**，不是从数据推算的，必须实现为集中的具名常量，上线后用真实数据校准。

### D22 阶段可变性（修订 D1、D3）

**结论**：**创建时**可基于模板在 3–7 段之间增删并改名；**创建后锁定**，只能改名。

**理由**：① 创建时还没有历史数据，调整阶段集合不付任何代价——这是唯一能改动阶段而不用付代价的时刻；② 创建后锁定，保住了"按下标对齐"这个让数据模型保持简单的关键简化；③ 不推翻 D1：D1 拒绝的是"从空白编辑器从零自建"，本决定仍然从模板出发；④ 把"模板必须一次定对"这个不可能的要求降级为"模板是个好起点"。

**被否**：① 阶段完全固定；② 创建后也可增删（需同时定义历史记录的对齐规则）。

### D23 模板内容

**结论**：

| 场景 | 默认阶段 |
| --- | --- |
| 运营 | 曝光 → 点击 → 注册 → 激活 → 留存 |
| 销售 | 线索 → 跟进 → 报价 → 成交 |
| 教培 | 试听 → 报名 → 到课 → 续费 |

**理由**：「运营」在多数公司默认指用户/内容/增长运营，其骨架对任何线上业务都成立，与"通用"定位一致；电商漏斗只适用于一个垂直行业。

**被否**：① 运营 = 电商型（曝光→加购→下单→支付→复购）；② 同时提供四套模板。

**术语限定**：本项目的「运营」特指内容/增长型运营，**不含电商运营**。

### D24 时间轴锚点

**结论**：锚在**最新一条记录的日期**并向前推窗口长度，不锚在今天；**展示范围与环比窗口是同一个参数**；轴上必须显式标注起止日期。

**理由**：使用者的心智是"看我手里这份数据"，不是"看日历"；锚在今天会让每周只导入一两次的使用者大部分时候看到空白图，认定产品坏了。**禁止省略中间空缺把不相邻的日期连成相邻点**——那是编造趋势。

**被否**：① 锚在今天、缺失留空；② 锚在今天并省略中间空缺。

### D25 MVP 页面与能力

见第 5 节。

### D26 数据跨度

**结论**：导入**不限天数、全部保存**；图表展示受窗口上限约束（最多 30 天）；导入成功后明确告知「已保存 N 天，当前展示最近 M 天」。

**理由**：把导入限制为 60 天（2 × 最大窗口）的截断**不可逆**——数据没存下来就永远没了；而多存数据的代价几乎为零（一年 365 条文档）。将来若要做季度趋势，只需新增更长的窗口档位，数据早就在库里，零迁移。

**被否**：① 限制导入为 60 天；② 让展示范围独立于环比窗口（恢复两个参数）。

### D27 日期解析

**结论**：接受 `2025-05-01`、`2025/5/1`、`2025年5月1日` 并规范化为同一格式；**无年份的一律拒绝**；同一批里出现重复日期则整批拒绝。日期不要求有序、也不要求连续。

**理由**：分隔符与"年月日"写法属于**格式**差异，不是语义差异，无损规范化不违背 P1；而无年份在跨年时补全必然无声出错（1 月贴去年 12 月的数据、或表里同时有 12/30 和 1/2）。重复日期必须整批拒绝：同一天给出两个不同数字时，系统没有依据判断哪个对，替使用者选就是编造。

**被否**：① 只接受一种日期格式；② 无年份时按最新数据所在年份自动补全。

## 5. MVP 功能边界

### 必须实现

**数据与权限**

- `funnels` / `records` 两个集合，结构如第 4 节
- 两个集合的安全规则都设为「仅创建者可读写」

**云函数**

- 导入数据：原子写入（`db.runTransaction`）、完整校验、报告全部问题位置、显式补 `_openid`
- 清空某漏斗的全部数据

**创建漏斗**

- 三套模板（D23）
- 创建时可增删阶段（3–7）、改阶段名、给漏斗命名

**导入数据**

- 读取剪贴板、按 D7 格式解析
- 一键转置（用户触发 + 失败提示）
- 按 D9 做无损规范化与原子校验，一次列全所有问题
- 预览 → 确认入库；成功后告知"已保存 N 天，当前展示最近 M 天"

**计算**

- 逐步转化率与整体转化率（D10）
- 除零与矛盾数据判定（D11）
- 环比（7/14/30，默认 7，不足则 `—`）
- 异常判定（规则式 + 样本量门槛 + 阈值常量化）

**呈现**

- 梯形漏斗：严格比例、内嵌 + 侧置标签、0 人虚线标记
- 折线图：整体/单步切换、异常打点、跨图表异常摘要、点开看依据
- 入口人数的独立呈现
- 时间轴锚点与起止日期标注
- 整体转化率（顶部）

**漏斗管理**

- 重命名漏斗、改阶段名、清空全部数据、删除漏斗

### 后续迭代

- 单日数据的删除与编辑（MVP 用"重贴覆盖 + 清空全部"兜底）
- 导出图片或数据
- 多漏斗对比
- 电商运营模板
- 自定义异常阈值（MVP 用集中常量）
- 分享与协作
- 创建后修改阶段结构（需先定义历史记录对齐规则）
- 更长的展示窗口（90 / 180 天，数据已在库、零迁移）
- 阶段名匹配失败时手动指定对应关系

## 6. 两处展示细节（已确认）

以下两点不影响任何数据口径，纯属展示与文案层面，已在访谈收尾时确认。

**其一，入口人数怎么"独立呈现"。** **结论：与折线图上下并列的小型趋势柱状图**（横轴为窗口内日期，纵轴为第一阶段人数）。理由是柱状图在视觉上与折线图区分明确，且"每天一个流量柱"的形状符合使用者对流量变化的直觉；用卡片只显示单点汇总会丢掉趋势，而入口人数的价值恰恰在趋势。

**其二，"人数比口径"的声明放在哪里。** D2 要求转化率口径必须在产品内可见。**结论：放在漏斗详情页整体转化率数字的下方**，一行浅色小字，例如「口径：各阶段人数之比，不做同批人去重」。理由是它紧跟那个最容易被误读的数字，用户在质疑"这个百分比准不准"时视线正好在这里；放进设置或"关于"弹层则几乎没人会看到。

## 7. 已知风险

1. **阈值未经校准。** 30% 与样本门槛 20 是猜测值。误报过多会让使用者关掉异常功能；建议上线后用真实数据回看。
2. **严格比例会让极端数据的末段几乎不可见。** 这是 D19 的有意选择，但可能引起"图是不是坏了"的疑问——0 人虚线标记与侧置标签是缓解手段，不保证足够。
3. **长窗口需要翻页。** 30 天视图 2 次请求、90 天 5 次（小程序端 20 条上限）。默认 7 天视图无此问题。
4. **改阶段名会让旧表匹配失败。** 使用者需要重新对照表头；手动指定对应关系在后续迭代。
5. **云函数漏写 `_openid` 是静默故障。** 必须在云函数里补一条"A 用户读不到 B 用户数据"的回归用例。
6. **小数据量用户的异常功能可能近乎失效。** 若某类用户的周数据只有几十人，样本门槛会让判定极少触发——这是刻意的取舍（宁可显式不判定，也不降低门槛制造假信号）。
7. **模板阶段必须一次修改到位。** D22 允许创建时增删，缓解了固定模板的死角，但模板本身若偏离真实流程太多，使用者每次建漏斗都要手工调整。
