# `records` 每条文档存一整天，阶段以数组内嵌在 `funnels` 中

`funnels` 文档内嵌有序的 `stages` 数组（阶段名与顺序）；`records` 每条文档表示某个漏斗某一天的数据，各阶段人数按与 `stages` 相同的下标组成 `counts` 数组。阶段身份由下标决定，而不是名称或独立字段。

## Considered Options

- **一条记录一个数字**（`funnelId, date, stageIndex, count`）：更接近规范化的写法，但 7 阶段 × 30 天会产生 210 条文档，而小程序端单次查询最多返回 20 条，取一次完整矩阵要翻十几页。
- **多列存储**（`stage1_count`…`stage7_count`）：三个模板阶段数为 4/5/7 不等，必须按最大值补齐并产生大量空值；后续放开自定义阶段时要迁移全部历史记录。
- **内嵌对象 map**（`{ 阶段名: 人数 }`）：阶段一改名就与历史数据脱钩。

## Consequences

- 一次查询即得整块漏斗矩阵；写入按「漏斗 + 日期」覆盖式更新，重复导入不产生脏数据。
- 阶段与人数靠下标对齐，因此阶段的数量与顺序必须在漏斗创建后保持稳定。这正是「创建时可增删阶段、创建后锁定、只能改名」这条规则的来源：创建时还没有历史数据，调整阶段集合不付任何代价；一旦有了记录，任何增删都必须先定义对齐规则（补零、按名称回填还是插位）。
- 若将来允许增删阶段，必须同时定义历史记录的对齐规则（补零、按名称回填还是插位）。
